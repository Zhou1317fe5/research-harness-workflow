### 使用原则

本模板是 checklist-style scaffold（查漏脚手架），不是 rigid format（固定版式）。

- Claude 可以先按问题本身自由组织 Spec，再用本模板查漏。
- 不强制每个 Spec 使用完全相同的章节顺序或篇幅。
- 普通轻量模块可以写短 Spec，只要关键事实、风险和验收标准清楚。
- 高风险模块按 `pre-run-implementation-review` 的风险分流补齐数据流、计算入口与评测口径证据。
- 不适用的条目写 `not_applicable` 或 `NOT RUN locally`，不要为了填满模板而制造内容。
- `REVIEW-01` 负责检查硬约束是否遗漏，不负责要求所有章节都写满。
- `experiment_type` 在 Scope 表中声明，枚举值见 §9.3 Claim Boundary；不同类型决定本轮可以声称什么、不能声称什么。

## Acceptance Criteria

### 9. Research Contract（实验前冻结，开始后不改）

> 本节是本轮实验的判据冻结。Hypothesis / Success Signal / Failure Signal / Metric & Split / Stop Condition 在首次远程运行启动前定稿，运行结束后不改写、不重新定义，避免"事后造判据"。Claim Boundary 由 Scope 中的 `experiment_type` 决定。

#### 9.0 判据分类与阻塞规则（实验前逐条标注）

> 每个判据在首次远程运行前必须标出**它验证什么**，因为这决定了它能不能独立阻塞实验。
> 分类错了会让与结论无关的检查挡在科学问题前面，历史上曾因此把一次可跑的对照实验压了数天。

| 类别 | 验证什么 | 未通过时 |
|------|----------|----------|
| **前提判据** | 会让本轮结论失真的东西：机制是否真的作用于输出（source→sink）、有无泄漏、baseline/采样/指标是否公平、结果归属是否正确、算子实现是否与理论一致、**以及任何可能改变候选排序 / 符号 / 方向 / 结论的精度问题** | **阻塞**：先解决，才能跑科学对照 |
| **诊断判据** | 不会改变本轮结论的精度、完备性、工程规范、无关边界处理 | **记录**：写进 validation gaps，照常推进 |

分类是对**本轮结论**而言的，不是对“精度”这个词而言的。同一项检查在一个任务里是诊断，在另一个任务里可能是前提（例如置信区间、top-k 稳定性、近似误差是否改变候选排序）。因此必须在实验前逐条写清楚“它到底在验什么、不通过会不会改变结论”，**不在事后自动豁免任何已批准的判据**。

四条规则：

1. 前提判据未通过 → 停止并说明；诊断判据未通过 → 照常推进，只记录。
2. **分类在实验前冻结。** 属于哪一类必须在本次运行开始前逐条写清，不得事后宣布“刚才那条只是诊断”。
3. 门禁报告未通过时，必须写明**是哪一条判据、属于哪一类**，不能只给一个布尔值。人问“卡在什么门禁上”必须能直接答出来。
4. **不为了通过判据而放宽阈值、挑更好看的结果，或接受来源不明的数值。** 改变判据本身属于合同变更，需重新批准并说明为什么新判据代表目标量。

**易错点**：数值精度类判据容易把两类混在一起。“算子实现是否与理论一致”是前提；“有限差分在某个步长下够不够准”是诊断——后者在验求导近似本身，与实现正确性无关，不应独立阻塞。

#### 9.0.1 阶段顺序：先问机制，再证正确

投资顺序决定进度。先花小钱看方向对不对，值得才花大钱把实现做精确；反过来会变成“正确性永远可以更正确”，而那个能回答“ idea 行不行”的对照一次都跑不了。

**四步顺序**：

1. **前提类判据 + 最小机制 screen（最便宜）**：机制确实到达输出、无泄漏、baseline/采样/指标公平，然后用最小设置跑一次对照。
2. **看信号决定下一步**：有信号才投入精度类校验与完整矩阵；没信号则进入下面的“无信号终态”。
3. **精度类校验与完整矩阵**：前置诊断收严，按预注册协议跑正式对照。
4. **写进结论**：只有走完第 3 步且证据质量足够的数值才能作为论文证据。

**顺序改变的是“科学投入”，不是运行前的适配性与接入校验**。`pre_review_smoke` 与科学 review 属于前提类（它们防的正是“代码错了→假阴性”），仍先于任何产出指标的运行。本节的改动是：**screen 先于精度校验与完整矩阵**，而不是“先跑 screen、再补审查”。现有 `remote_route.py` 仍要求有代码变更的 official 运行先通过这两道，原文未变。

**小规模 official screen 本来就可做**：官方运行不强制全量规模（`max_steps` / `gpu_count` 约束只作用于 `pre_review_smoke`），所以“先跑一个便宜但真实的对照”不需要新机制，只需要在 spec 里把第一阶段就写成这个 screen，而不是先写精度门。

**省的是诊断，不是前提**：机制未到达输出、泄漏、对比不公平这三类仍然必须在 screen 之前成立。它们便宜且决定性——特别是“**机制到底有没有改变输出**”这一个判断，它比“有限差分准不准”便宜得多，却能分开两类完全不同的失败。

**关于“代码错了导致没效果”**：这是最需要防的假阴性。分情况看：

- **输出完全没变**：强烈提示接口 / 接线问题（前提类），优先查代码。但这**不是充分证据**——“输出未变”有合法来源：方法合法地拒绝了所有候选、回退到了 baseline、初始化为零、或最终决策本来就不敏感。要区分开，得看机制内部是否确实消费了候选，而不是只看最终指标不动。
- **输出变了但指标没改善**：需要判断是精度问题还是机制问题。**两者都还没被排除**时不得下任何关于 idea 的结论。

因此“先问机制”绝不意味着“实现可以随便错”：它只是把**便宜且决定性**的检查提到前面，先把“接线问题”和“机制问题”分开，再决定钱往哪投。

#### 9.0.2 “无信号”是正式终态，不是失败

流程原先只有“通过/卡住”两个结局，没有“跑了、没信号、收工”这一种。后果是执行者只能选择继续把前置做到完美——它没有别的选项。

- 允许将“**本次未观察到预注册收益**”作为正常收工结论关闭 Mission，不必当作失败或未完成。
- **只有在本次证据质量足以支撑否定时才写“Hypothesis 被否”**：需要足够的样本量 / 重复、实现已验证、并且真正达到 9.2 定义的 Failure Signal。实现未验证、样本过小或信号在噪声内时，正确写法是 **“inconclusive / 未观察到收益，原因待查”**，不是“已证否”。两种写法都允许收工，区分在结论强度。
- **小规模结果不作为 idea 的最终证据**；本次能否用于论文取决于实际协议、样本量、选择偏差与可复核证据，**不是**简单地“走完某一步就自动合格”。
- 看到正向信号也不等于 idea 已验证：它只说明值得投后续校验。
- 不是新增门禁：它不阻止任何运行，只是给“停下来”一个合法出口。

#### 9.3 Claim Boundary（由 Scope 中的 `experiment_type` 决定）

| experiment_type | 可声明 | 禁止声明 |
|-----------------|--------|----------|
| `baseline_reproduction` | "对齐论文数字"或"复现失败 + 偏差量化" | 不声明方法带来的 <主指标> 提升，不据此更换当前采用模型 |
| `probe` | tentative 趋势、需 follow-up | 不作为 STATE 已验证结果；标 "tentative / 待 seed audit" |
| `method`（单 seed） | tentative <主指标>，标注 seed | 不作为 STATE 已验证结果 |
| `method`（多 seed） | <主指标> ± std，可作为 STATE 已验证结果 | 不声称"超过 SOTA"除非完整对齐对照协议 |
| `ablation` | 组件贡献度，如 "+1.2 <主指标> from X module" | 不声称新 SOTA，不据此更换对照原点 |
| `seed_audit` | 稳定性结论（std / 区间） | 单 seed 不作为 STATE 已验证结果 |
| `reproducibility` | 自家方法复现自检结论 | 不声称新结果 |
