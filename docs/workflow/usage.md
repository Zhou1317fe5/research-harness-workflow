# 用一轮实验走完：讨论、CSV、Goal，再到结果分析

假设项目已经接好工作流，基线也有了结果。现在想验证一个新采样策略，看看它在相同评测条件下能否带来改善。

下面就用这个例子走一遍。还没有接入项目的话，先看[接入教程](installation.md)。

## 先讨论这一轮到底要验证什么

可以在 Claude Code 里讨论，也可以用 Codex。先把现有结果和这次想改的部分放在一起：

```text
mission 我想在现有基线上验证一种新采样策略。

先读取当前研究状态和已有基线结果。
本轮只改采样策略，沿用网络结构、数据划分和评测口径。
请和我讨论对照怎么做、主指标怎么看、需要多少运行预算，以及什么情况下停止。
先形成实验方案，暂不实现和启动训练。
```

这里最值得花时间的是“怎么比较”。原来的基线用了哪些设置，新方案准备保留哪些设置，重复几次才能回答问题，都应该在方案里说清楚。

能从代码和已有记录中查到的内容，交给 agent 去查。真正需要你决定的，是这轮研究目标、可接受的投入，以及验收口径。

讨论差不多以后，让它把共识写进 Spec。阅读时重点看目标、对照、预算和交付要求，确认这份方案确实描述了你要做的实验。

如果你已明确委托 agent 在本任务范围内批准方案，它会在 spec 中记录 `approval_mode: delegated` 和授权来源，继续推进。记忆队列中的 pending 只是尚未整理，不会撤销这项授权。

## 把批准的方案转成 CSV

接下来要得到的是执行清单。除了实现采样策略，还应包含行为验证、必要的运行前检查、正式实验、结果分析和最终验收。

如果准备把执行交给后面的 Goal，可以这样结束方案阶段：

```text
批准这份方案。
请保存批准状态并提交方案，再用 mission 生成对应的任务 CSV。
这一步做到 CSV 准备完成即可，后续由 Codex 的 Goal 模式执行。
```

把“做到哪里”说清楚，是为了给讨论与执行留一个明确的交接点。工作流本身也支持从批准的方案继续执行；需要分开使用时，就明确本次先交付 CSV。

拿到清单后，可以快速看一遍是否漏了结果分析和最终验收。只列“改代码、启动训练”，还不足以把这轮研究做完。

## 用 Goal 模式执行 CSV

现在切到负责执行的 Codex，把刚才的 CSV 交给它：

```text
/goal 按仓库的 CSV 执行流程完成 @issues/<任务目录>/<任务清单>.csv，逐项验证、整理结果并完成提交。
```

`/goal` 后面是要完成的目标，`@` 引用的是实际 CSV 文件。把占位路径换成项目刚生成的那份清单。

执行时仍然遵循仓库的 `mission-csv-execute` 流程。CSV 记录任务与进度，Goal 让同一个会话跨回合继续推进；结束标准来自这份清单及其验收要求。

普通模式也可以输入：

```text
mission issues/<任务目录>/<任务清单>.csv
```

它同样进入 CSV 执行，但不会自动开启 Codex 的 Goal 模式。长任务可以直接选择上面的 Goal 用法，无需对同一份 CSV 再发一遍启动指令。

Goal 的功能设置和控制方式见 [OpenAI Docs](https://developers.openai.com/codex/use-cases/follow-goals)。任务完成、用户暂停、达到所设预算或遇到真实阻塞时，按实际情况停止；未完成的工作仍保留在 CSV 中。

## Codex 接下来会做什么

首先是读项目、修改代码、做本地验证。对采样策略这个例子，至少要确认参数真的传到了采样逻辑，输出行为符合约定，相关检查没有被改坏。

训练和评估参数在项目的 `.sh` 脚本中调整，例如 `scripts/train.sh`、`scripts/eval.sh`，或单个 `scripts/train_eval.sh`。工作流调用 `bash <脚本>`；`project.toml` 只登记入口、阶段和输出约定。已有脚本沿用原来的路径，脚本和代码一起提交，实验记录据此关联实际版本。

涉及科学计算的改动，还要按风险完成真实短运行和必要的实施审查。短运行能帮助发现入口、数据和计算是否跑得起来；审查则要核对实际实现是否符合方案。通过这些步骤后，再进入正式训练或评估。

过程中发现的问题，会回到相应任务里修复并验证。已经授权、能够按现有条件处理的事情继续推进；需要改变实验目标或投入时，再讨论新的决定。

最后还有整体验收。它要回头检查：这轮任务原本想回答的问题，是否已经有相应结果和证据。每项都写了“完成”，也要能找到支持这个状态的材料。

## 训练开始以后，安心等的是哪一部分

长训练交给 rrctl。它先确认实验有真实进展，再按约定检查状态。agent 在同一会话中等待结果，完成或出现需要处理的异常后，继续原来的 CSV。

这时不需要隔一会儿问一次“跑到哪里了”。想了解进度当然可以直接问，但正常等待应该由程序承担，减少重复读日志和生成进度分析的模型调用。

Goal 模式也沿用这一做法：继续等待同一个 rrctl 进程，拿到新结果再处理。工作流没有把训练等待变成一个定时唤醒 agent 写汇报的任务。

日志停了一小会儿，要结合保存 checkpoint、数据读取等情况复核。进程退出后，则要判断正常完成、失败还是主动停止。失败时先看已有诊断证据，再依据预算和停止条件处理当前任务。

## 想暂停，或者中途断了

先分清暂停的是哪件事。暂停 agent 继续推进任务，和停止远端正在进行的训练，是两个动作。

Goal 模式下，可以用：

```text
/goal
/goal pause
/goal resume
```

它们分别用于查看目标、暂停推进和恢复。`/goal pause` 不会自动停止已经启动的远程训练。确实要停训练时，在请求里明确说明，由 agent 核对并处理当前运行。

恢复工作前，先看 Goal 和 CSV 的实际状态。普通模式下，或者需要重新定位未完成任务时，可以输入 `mission`；知道路径就直接给出那份 CSV。核对已有进展之后继续，避免把尚在运行的实验重新启动。

当前任务由本地 `issues/.missions.json` 保存，优先于其他 CSV 的修改时间。尚未生成 CSV 时也能沿登记的 spec 指针恢复。取消或被替换的任务不再进入恢复候选；暂停的任务需要明确恢复，未完成的 CSV 行保持真实状态。这个本地控制文件不随代码分支回退，转移工作区时应一起保留。

agent 通过以下命令记录生命周期，例如取消任务：

```bash
python .agents/harness/workflow/mission_state.py transition --task-id <task-id> --status cancelled --source-ref <本次用户指令引用> --reason "用户取消任务"
```

切换新任务时，注册新 spec 并添加 `--replaces <old-task-id> --reason <原因>`，新指针和旧任务退休在同一次写入完成。生命周期不会代替你停止远端训练。

## 等结果出来，先看这几件事

先回到最初的采样策略问题。新方案和基线是否使用了约定的评测条件？改动有没有真正生效？观察到的差异有多少证据支持？还有哪些地方没有验证？

这些内容应该出现在实验分析和交付说明里。一个正常退出的训练进程，还不能单独回答新策略有没有用。

阅读时可以沿着下面的顺序：

1. 先看任务的 handoff，了解本轮完成了什么、还缺什么。
2. 再看对应实验的分析，核对结果、发现和下一步建议。
3. 对某个结论有疑问时，沿引用找到代码、原始指标或日志。

常用位置放在这里，熟悉后就不用从整个项目里找：

| 想看什么 | 位置 |
|---|---|
| 当前研究进展 | `research_workspace/STATE.md` |
| 仍然有效的研究结论 | `research_workspace/CONCLUSIONS.md` |
| 已有实验索引 | `research_workspace/EXPERIMENTS.csv` |
| 某次实验的分析 | `research_workspace/experiments/<ExpID>/analysis/analysis.md` |
| 本轮 review 与 handoff | `issues/<任务目录>/` |
| 原始运行证据 | `remote_artifacts/<ExpID>/<RunID>/` |

代码和 `research_workspace` 分别提交、分别推送。代码仓库推送成功，并不表示科研记录也已经推送；交付时需要分别检查。

## 科研记录与召回

假设这一轮发现：新采样策略只在某种条件下有改善，其他条件下没有稳定收益。下一轮讨论时，这个范围应该一起带回来。

可以这样开始：

```text
请先读取当前研究状态和结论，再查看上一轮采样策略实验的分析。
总结已经得到支持的发现、还不确定的部分，以及现有证据适用的条件。
接下来我想讨论是否继续这个方向，先不要启动新实验。
```

工作流会保留讨论和分析的来源，再由 agent 整理当前决定与发现。一个“可以试试”的建议先作为想法保留，有了实验依据再判断它能否成为结论。

方案改变时，旧记录仍然可查，并说明它被什么决定取代。失败的尝试、没有提升的实验，也能帮助下一轮缩小范围。

Hindsight 可以辅助寻找较远的历史材料，但检索到相似内容后，仍要核对来源和适用条件。它的[官方安装仓库与接入方法](installation.md#可选-hindsight)在配置教程里，本地记录功能也能独立使用。

Hindsight 默认关闭自动同步。启用后，远端只接收已整理的精简记录和明确发布的完成版分析；普通消息和后台 Historian 提示词留在采集边界之外。需要同步时运行 `research_memory.py sync`，需要查历史时再 recall。

若状态文件被恢复到旧版本，记忆程序会报告投影冲突。用 `research_memory.py recover --repair-projections` 核对并修复受管理区域，不用 `git restore` 撤销新的用户决定。

## 只是整理已有结果时

画图、选样例、撰写论文正文，可以直接提出请求：

```text
请根据已有实验结果整理一张对比图。
保留各实验的评测条件和来源，不新增实验。
```

这类工作通常不需要再建一轮实验清单。如果分析中发现还需要补实验，就把新问题带回方案讨论，明确新的目标和运行范围。
