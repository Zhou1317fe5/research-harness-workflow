# 日常使用指南

接入并完成[项目接入与配置](installation.md)后，在项目目录中打开 agent。实验目标、预算和评测条件尽量说清楚，执行细节由工作流按项目配置组织。

## 提出一轮新实验

可以直接描述研究目标：

```text
mission 我想在现有基线上验证一个改动。
请先结合当前结果讨论实验方案，明确对照、主指标和运行预算。
```

随后补充具体改动和约束。agent 会整理方案草稿；你确认后，再转成任务 CSV 执行。想修改方案时，在批准前说明。执行中出现新的需求，也应先更新任务范围。

已有方案时，可以直接给出路径，工作流会先核对其批准状态：

```text
mission docs/specs/<实验方案>.md
```

## 用 Goal 模式执行 CSV

执行依据始终是任务 CSV。Mission 提供从方案到任务清单、再到执行的工作流；Codex 的 Goal 模式让同一个会话跨回合持续推进目标。两者可以配合使用。

CSV 准备好后，Codex 长任务推荐在 Goal 模式中引用这份文件。在支持该功能的 Codex CLI 中，用 /goal 描述目标，并通过 @ 引用 CSV，例如：

```text
/goal 按仓库的 CSV 执行流程完成 @issues/<任务目录>/<任务清单>.csv，逐项验证、整理结果并完成提交。
```

这里的 @ 用来引用文件，Goal 的目标是完成指定 CSV，任务进度和验收依据仍写回这份 CSV。执行时沿用仓库的 mission-csv-execute 流程，包含验证、必要审查、远程运行和结果交付。

普通模式也可以直接使用：

```text
mission issues/<任务目录>/<任务清单>.csv
```

两种方式选一种发起即可，无需对同一任务重复发送。mission 命令本身不会自动开启 Codex Goal 模式；Goal 也不改变 CSV 的任务范围和完成标准。

| 你当前要做什么 | 使用方式 |
|---|---|
| 讨论新实验，准备方案与 CSV | mission 加研究需求或方案路径 |
| 在 Codex 中持续推进已有 CSV | Goal 模式引用 CSV，明确验收与交付目标 |
| 普通模式执行已有 CSV | mission 加 CSV 路径 |

只有 CSV 中的工作经过实际验证并完成所需交付，才能把目标视为完成。用户暂停、达到设置的预算或遇到真实阻塞时，保留未完成进度。Goal 的使用条件和控制方式见 [OpenAI Docs：Follow a goal](https://developers.openai.com/codex/use-cases/follow-goals)。

## 训练期间怎样配合

agent 按任务清单完成实现、验证、必要审查和远程运行。已授权的日常操作会继续推进，需要改变目标、预算或验收标准时再讨论。

长训练由 rrctl 负责运行和检查。保持同一会话等待时，完成或失败的结果返回后，agent 会继续当前任务。正常等待期间无需反复要求进度汇报；需要了解情况时，可以直接问当前状态。

使用 Goal 时也继续等待同一个 rrctl 进程，避免每个续轮重新查询训练和生成进度分析。Goal 负责持续推进目标，训练期间的检查仍由 rrctl 承担。

启动后会先确认实验产生了有效进展，再进入正常等待。日志短暂停顿或保存模型时变慢，需要结合运行情况复核；运行退出后也要区分成功、失败和主动停止。

失败时，agent 根据已有运行记录和诊断证据处理当前任务。远程完成后，先核对结果是否齐全、是否属于本次实验，再进入分析。

如果想暂停或调整范围，明确说明即可。暂停后续任务和停止正在运行的训练是两个动作，最好说明是否需要停止远端运行。

使用 Goal 时，可以用 /goal 查看目标，/goal pause 暂停推进，/goal resume 恢复。暂停 Goal 不等于停止已经启动的远程训练。

普通模式下恢复任务，或者需要重新定位未完成的 CSV 时，可以在项目中输入：

```text
mission
```

agent 会先寻找尚未完成的任务，核对已有进度再继续。知道具体任务路径时，直接指定 CSV 更清楚。

## 完成后看什么

先看这轮实验的结论、证据和仍未验证的部分，再决定下一步。运行成功与研究假设成立需要分别判断。

| 想了解的内容 | 从哪里看 |
|---|---|
| 当前研究进展 | research_workspace/STATE.md |
| 仍然有效的研究结论 | research_workspace/CONCLUSIONS.md |
| 做过哪些实验 | research_workspace/EXPERIMENTS.csv |
| 某次实验的分析 | research_workspace/experiments/<ExpID>/analysis/analysis.md |
| 当前任务的交付说明 | issues/<任务目录>/ 下的 review 和 handoff 文档 |
| 需要核验的原始结果 | remote_artifacts/<ExpID>/<RunID>/ |

实验索引和事实记录由工作流生成，修改研究判断时更新分析及结论，并保留依据。代码和 research_workspace 使用各自的 Git 历史，提交与推送也分别进行。

## 科研记录与召回

讨论出现新决定或实验分析发生变化时，工作流先保留来源，再由 agent 结合当前任务整理。已经明确的决定可以继续执行，尚未确认的内容则保留为待讨论事项。

例如，“可以试试增加一个模块”是一项建议，“下一轮采用这个模块”才是确认后的决定。“程序跑完了”描述执行事实，而“模块带来了稳定提升”还需要可比较的实验支持。记录时分清这些内容，避免后续把想法当成已验证的方法。

方案改变时，旧记录保留，并说明被什么决定取代。失败经验和没有提升的实验也会留下依据，帮助后续设计实验。查到相似结论后，仍需核对它的数据、评测条件和适用范围。

可以直接问“当前方案为什么这样选”“之前试过这个方向吗”，由 agent 沿记录核对来源。开始下一轮时，先读当前进展和相关结论，只有需要验证细节时才查原始日志。

Hindsight 是可选的辅助检索服务，帮助从较多历史材料中寻找相关来源。项目内的正式记录仍是核对当前决定和实验依据的起点；本地功能可独立使用。安装仓库和连接方法见[接入教程](installation.md#可选-hindsight)。

## 使用已有结果

画图、选择样例、撰写论文正文或复用已有结果，可以直接提出请求：

```text
请根据已有实验结果整理一张对比图，保留各实验的评测条件和来源。
```

这类任务通常不需要新建实验任务清单。若需要新增运行、产生新指标或新的基线对照，再进入新的实验方案与执行流程。
