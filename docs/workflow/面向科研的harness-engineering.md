# 面向科研的 Harness Engineering：用 Agent 做实验的思想与工作流

> 这套工作流最初是在一篇社区教程 [面向小白的 harness engineering 实战](https://linux.do/t/topic/2260154/1)
> 的基础上改出来的。那篇讲的是怎么把 agent + 任务清单这套架构在科研项目里搭起来；
> 本文讲的是**为什么这么设计**、**一轮实验怎么走**、以及**每个部分在管什么**，方便你改成自己的。

用 AI 做科研，跑得住的关键不是模型多聪明或者工具多，而是一个判断：

> 科研 harness 要管的是**上下文、实验前的判据、远程运行的证据、结果归档和当前结论**。
> 让 AI 在边界清楚的地方快速执行，让人保留问题定义、验收标准和科研判断。

---

## 一、几条原则

现阶段可靠的 AI 科研不是全自动，而是人在环里的半自动。AI 适合做重复劳动、代码实现、
实验调度、日志整理和初步分析；危险的是让它在混乱的上下文里自己定义问题、自己判断成功、
自己解释结果。下面几条是这套工作流所有机制的来源。

### 1. 上下文比工具数量重要

重点不是把材料一股脑塞进去，而是让模型只读**当前这件事需要的那部分**。

常见的污染：主会话里混进环境安装报错、下载日志、无关论文摘要；一个模型既搜论文又提想法
又写实现，最后困在自己前面说过的话里；旧实验的结论和当前事实混在一起，下一轮就把已经废弃的
东西当成真的。

对策是一个习惯：**把"当前在做什么""这次实验的事实""跨实验的结论""原始日志"分开存、分开读**。
文件只是载体，真正要管的是这些东西进入模型的顺序和粒度。

### 2. Baseline 是锚点，不是前置杂活

最常见的翻车方式，是让 AI 直接提一个想法，然后从零写一套代码去验证。没有 baseline 的
AI 科研几乎一定会飘。深度学习里多数有价值的工作也不是从零造系统，而是在一个跑得通、
信得过的 baseline 上做控制变量。**一个新想法值不值钱，只有在同一个 baseline、
同样的评测口径下才比得出来。**

### 3. 实验前把判断标准定死

AI 很擅长事后解释：结果没提升，它能说"发现了有趣现象"；对照失败，它能建议"再试个变体"。
只要事先没约定什么算成功，整个过程就会滑向先射箭再画靶。

所以在写代码之前，就要把**想验证什么、什么结果算成功、什么结果算失败该停、跟谁比**写下来。
尤其"失败"要单独定义清楚，而不是留成"没成功"的反面 —— 否则跑完总能圆回来。

### 4. 想法应该从实验信号里长出来

好想法很少凭空拍出来，多半来自某个卡点、某个反常结果、某张不对劲的可视化。
所以每个新实验都该先说清楚它**从哪来**：上一轮的失败逼出来的，还是某个异常结果、
某篇论文的启发。**AI 可以把想法的数量扩出去，但方向最好由真实信号约束。**

### 5. 远程训练不能只看"已启动"

最烧钱的部分在远程 GPU。命令发上去之后，系统会以为它在跑，但它可能第一秒就挂了，
或者显卡根本没占上、日志半天不动、跑完没产出结果，而人还在等。

**启动之后第一件事不是走开，而是先确认它到底有没有真的在跑。**
远程实验的第一目标不是自动化，是知道它有没有真实发生。

### 6. 工具要少而准

工具越多，模型越容易犹豫、误选，或者被工具输出拖垮上下文。让工具分工清楚：
本地代码理解、精确字符串定位、外部检索、远程运行、结果归档，各一件顺手的就够。
**工具是为了减少污染和重复劳动，不是为了堆能力。**

## 二、一轮实验怎么走

```text
① 定方案  →  ② 转执行清单  →  ③ 写代码 + 本地验证  →  ④ 运行前审查
                                                          │
⑦ 更新结论  ←  ⑥ 拉回证据  ←  ⑤ 远程训练/评估  ←────────┘
     │
     └→ 进入下一轮 ①
```

**① 定方案。** 先读当前状态和上一轮结果，把这轮要用的东西聚齐 —— 相关代码、上一轮日志，
必要时查文献。然后讨论这轮验证什么假设、怎么设计、什么算成功什么算失败，收敛成一份 spec。
这是整条链里最该慢下来的地方，也是人和 AI 一起做判断的地方。**spec 要你逐字确认才算批准。**

**② 转执行清单。** 批准的 spec 转成一份 CSV。这份 CSV 是执行状态的唯一来源 ——
每条任务的进度、验证、提交都记在上面，中断了也能从它恢复。

**③ 写代码 + 本地验证。** 按清单实现，跑本地的小验证：能不能导入、能不能编译、
参数有没有真的传到该去的地方。这些便宜、快、结果确定的检查放本地做。

**④ 运行前审查。** 推远程之前先过一道。这道门的存在理由见第四节 ——
简单说，科研的翻车方式是"代码全对、测试全绿、GPU 跑了二十小时，方法却是错的"，
而这个代价发生在"做出来"和"审查"之间。

按改动风险分档：文档、状态、纯测试的改动不用审；只改运行绑定、科学内容没变的，
探针过了就放行；改了模型、损失、数据、指标、计算入口的，要先跑一次隔离的短 smoke
（1–100 步），再做一次独立审查。

**⑤ 远程训练/评估。** 通过 rrctl 提交到远程 GPU。启动后 30 秒到 2 分钟内做一次首步检查：
进程在不在、有没有出现第 1 步、loss 是不是有限值、显卡占上没有、checkpoint 目录建了没有。
过了才算真的在跑；不过就别走开。之后转低频巡检，不用一直盯着。

**⑥ 拉回证据。** 只拉结论需要的部分 —— 结果文件、指标摘要、必要日志。
逐样本的追踪数据留在远端，要查再定点取。

**⑦ 更新结论。** 基于真实结果判断：假设成立没有、有没有反常信号、能得出什么结论。
然后更新三处：这次实验的事实（`record.json`）、这次实验的结论（`analysis.md`）、
如果认知真的变了，更新跨实验的结论（`CONCLUSIONS.md`）。

人始终握着"要不要这么干、结果能不能这么说"的判断权。

## 三、装在哪、怎么开始

**按项目安装，不装到全局。** 把仓库内容复制进你的项目目录，每个项目一份，互不干扰。
详细步骤见 [README](../../README.md)。

复制完项目里会有：

```text
.claude/skills/   .codex/skills/    两套 agent skills，内容一致
.agents/skills                     Codex 发现入口，链接到 .codex/skills
CLAUDE.md  AGENTS.md                agent 读的规则
.agents/harness/                    公共脚本与项目配置
  remote/rrctl/                    rrctl 独立 Python 包
issues/TEMPLATE.csv                 CSV 的列定义
docs/specs/                         实验方案
research_workspace/                 科研结论层
remote_artifacts/                   原始日志和结果
```

上手三步：

1. **给项目 `git init`。** 执行过程每完成一步会提交，没有 git 这条链会断。
2. **填 `CLAUDE.md` 末尾的「本项目补充」** —— 研究方向、baseline、主指标、canonical 文件、
   远程环境路径。前面的通用规则不用动。
3. **先跑一轮简单的。** 别挑复杂模块，选个 baseline 复现或简单实验，
   目的是验证这条链能不能走通。

另外两个可选工具需要单独装：`fast_context_search`（本地代码语义检索）、
`smart-search-cli`（外部资料检索，结果可落盘存证）。

## 四、各部分在管什么

分两层：**规则层**（给 agent 看的）和**结论层**（人和 agent 共享的）。

### 规则层

| 文件 | 管什么 | 你改它会怎样 |
|---|---|---|
| `CLAUDE.md` / `AGENTS.md` | agent 的路由、硬约束、项目事实。两个文件内容相同，各自宿主读各自的 | 改行为规则；末尾「本项目补充」放项目事实 |
| `.claude/skills/` `.codex/skills/` | 各阶段的具体流程。两套内容一致，**改规则时两边都要改** | 增删能力 |
| `docs/specs/TEMPLATE-spec.md` | 一份方案该写哪些字段 | 增减每轮实验固定要回答的问题 |
| `issues/TEMPLATE.csv` | CSV 的列和状态枚举 | 调整任务状态机 |

skills 的分工不按宿主分，按阶段分：

- `mission` —— 路由。判断输入是需求、方案、CSV 还是恢复请求，转给对应的下一步
- `mission-spec` —— 需求讨论，产出 spec，等你确认
- `mission-approved-doc` —— 已批准的 spec 转成 CSV
- `mission-csv-execute` —— 按 CSV 一行行执行到完成
- `mission-recovery` —— 找出没做完的任务接着做
- `pre-run-implementation-review` —— 跑 GPU 前的科学审查
- `remote-run-snippet` —— 按项目配置组织训练与评估，交给 rrctl 运行、监控和拉取
- `research-result-commit` —— 研究产物合并提交
- `systematic-debugging` —— 根因不明时的定位辅助

### 结论层

```text
remote_artifacts/<ExpID>/<RunID>/   原始日志和结果。项目根，不进 Git
research_workspace/
  STATE.md              当前在做什么，1–3 屏
  CONCLUSIONS.md        现在相信什么、否定什么
  EXPERIMENTS.csv       做过哪些实验，自动生成
  experiments/<ExpID>/
    record.json             这次实验的事实，自动生成
    analysis/analysis.md    这次实验的结论，四段：Change / Result / Finding / Next
```

三个文件各回答一个问题，不重叠：

| 文件 | 只回答 | 谁写 |
|---|---|---|
| `STATE.md` | 当前在做什么 | 人审核 |
| `CONCLUSIONS.md` | 现在相信 / 否定什么 | 认知真的变了才动 |
| `EXPERIMENTS.csv` | 做过哪些实验、彼此什么关系 | 脚本生成 |

**读的顺序是设计的一部分**：`STATE.md → CONCLUSIONS.md → EXPERIMENTS.csv → record.json → analysis.md`，
只有要核对某次实验的细节时，才下到 `remote_artifacts/`。平时不读原始日志，
上下文就不会被无关内容占满。这是第 1 条原则的落地。

**为什么不用一个大文件记所有实验。** 单文件台账在几十次实验之后必然变成"写了没人读"。
它靠正则匹配表头插行来更新，结构上就容易乱。而每个实验一个 `record.json`、格式固定，
出错空间小得多。

**实验之间的关系靠 `record.json` 的 `parent` 字段**记录 —— 这个实验是从哪个实验改来的、
是对照还是复现。有了它就不用另外维护一张关系图。

### 配套脚本

- `.agents/harness/records/experiment_records.py` —— 从 CSV 和证据生成 `record.json`，再汇总成 `EXPERIMENTS.csv`。
  它**不会替你判断哪一组是对照组** —— 那是判断，不是能从文件里读出来的事实，
  所以这类字段会留空并列进 `_pending`，等你补。
- `.agents/harness/remote/build_rrctl_runspec.py` —— 构造远程运行请求并做契约校验。
- `.agents/harness/pipeline/run_pipeline.py` —— 按配置依次执行训练和评估，检查 checkpoint 与结果文件。
- `.agents/harness/remote/remote_run.py` —— 串联 rrctl 的 ready、launch、wait 和 pull。
- `.agents/harness/remote/adapters/` —— 远程 adapter，默认只有通用的一个。
  项目专属的登记在 `project_adapters.py`，不用改主程序。

## 五、改成自己的

工作流目录 `issues/`、`docs/specs/`、`research_workspace/`、`remote_artifacts/` 保持不动。
项目接入时修改以下几处，具体示例见 [用户配置说明](../../.agents/harness/docs/configuration.md)：

- `.agents/harness/config/project.toml`：填写真实训练、评估命令，checkpoint 衔接、日志路径和产物清单。
  `adapter` 映射已有进度与结果字段，`records` 映射主指标、辅助指标及项目实际使用的运行维度，
  无需修改实验记录脚本。
- `.agents/harness/config/profiles.json`：填写远程连接。密码只通过 `password_env` 引用变量名。
- `.agents/harness/config/.env`：保存凭据和远程环境设置。此文件与 `profiles.json` 均不提交。
- `AGENTS.md`、`CLAUDE.md` 末尾：同步填写“研究背景”和“路径”，说明 baseline、评测口径及项目入口。

项目已有日志目录可以保留，只需让本次运行的输出归入独立的 `output_root`，并配置相对路径。
文本日志可直接拉取；自动判断进度和完成状态需要结构化字段或项目 adapter。
成功结果和异常诊断都由 `rrctl pull` 拉取，诊断使用 `--diagnostic`，不再单独维护拉取 skill。

建议先用最小链路跑顺几轮（baseline 复现、简单实验），熟悉了讨论 → 执行 → 远程 → 归档
这条线之后，再往上加复杂模块。

## 六、最后

这套东西的核心不是自动化程度，而是**边界**。

AI 在边界清楚的地方效率很高：实现一个已经想清楚的方案、跑一批已经定好的实验、
整理一堆日志、做初步分析。边界模糊的地方它会飘：什么问题值得做、这个结果能不能这么解释、
这条路线该不该停。

所以这套工作流做的所有事，本质上都是在**把边界画清楚**：
spec 把"要验证什么"定死，CSV 把"做到哪一步了"定死，运行前审查把"方法对不对"定死，
证据层把"跑出了什么"和"我们相信什么"分开。

画清楚之后，AI 可以在里面跑得很快。画不清楚，跑得越快错得越远。
