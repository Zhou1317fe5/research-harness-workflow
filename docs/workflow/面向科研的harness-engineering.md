# 面向科研的 Harness Engineering：用 Agent 做实验的思想与工作流

> 本文是在一篇社区实战教程 [面向小白的 harness engineering 实战（科研导向的 infra 搭建）](https://linux.do/t/topic/2260154/1)的基础上做的优化。那篇教程解决的是"怎么把 Claude + Codex + mission/`goal` 这套架构在科研项目里搭起来、跑通闭环"；本文假设你已经理解那套架构，重点讲**与 AI 合作做科研的思想**、**这套工作流仓库怎么用**、以及**仓库各部分是干什么的**，方便你按自己的课题改造。
>
> 另一个主要动机是 **token 消耗**：原流程在上下文管理上偏粗，主会话容易被无关材料、重复读取和过长的历史撑大；再加上它直接挂载了整套完整的 superpowers skills，光是这套 skill 本身就非常吃 token。本文这套流程一方面精简了挂载的 skill，只留科研实验真正用得上的少数几组；另一方面把上下文分层管理、"先读当前真相再按需追历史"，减少 token 消耗。

这篇文章分享的是用 AI 做深度学习科研的一套工作流，以及它背后的思想。它不是"装几个 MCP / skill，然后让 AI 自动发论文"的教程。真正让它跑得住的，不是某个模型多聪明，也不是工具多，而是一个判断：

> 科研 harness 的重点，不是让 AI 永不停歇地跑，而是把**上下文、实验前判据、远程运行证据、结果归档和当前真相**管理起来。让 AI 在边界清楚的地方高速执行，让人保留问题表述、验收标准和科研判断。

下面先讲思想，再讲工作流大致怎么走，最后讲这套仓库怎么用、怎么改成你自己的。

---

## 一、核心思想：与 AI 合作做科研的几条原则

现阶段最可靠的 AI 科研不是 full-auto research，而是 human-in-the-loop 的半自动系统。AI 很适合做重复劳动、代码实现、实验调度、日志整理和初步分析；真正危险的，是让它在脏上下文里自己定义问题、自己判断成功、自己解释结果。下面几条原则，是这套工作流所有机制的来源。

### 1. 上下文比工具数量更重要

`Context Is All You Need`——但重点不是把所有材料一股脑塞进去，而是让模型只读**当前任务需要的那份干净上下文**。

典型的污染很常见：主会话里混进环境安装报错、下载日志、无关论文摘要；一个模型既搜论文又提 idea 又写实现，最后越来越困在自己前面说过的话里；旧实验的结论和当前事实混在一起，下一轮就把已经废弃的东西当成真相。

对策不是某个具体文件，而是一个习惯：**把"当前真相""单轮交接""单次分析""路线复盘""外部证据"这几类东西分开存、分开喂**，谁也别污染谁。文件只是载体，真正要管理的是上下文进入模型的顺序和颗粒度。

### 2. Baseline 是锚点，不是前置杂活

最常见的翻车方式，是让 AI 直接 propose 一个 idea，然后从零写一套代码去验证。没有 baseline 的 AI 科研几乎一定会飘。深度学习里多数有价值的工作，本来也不是从零造一套系统，而是在一个跑得通、信得过的 baseline 上做控制变量、看真实信号。**一个新想法值不值钱，只能放在同一个 baseline、同样的评测口径下才比得出来。**

### 3. 实验前要把判断标准定死

AI 极擅长事后解释：结果没提升，它能说"发现了有趣现象"；某个对照失败，它能建议"再试个变体"。只要事先没约定好什么算成功，整个过程就会滑向先射箭再画靶。

所以更稳的做法是：**在写代码之前，就把"想验证什么假设、什么结果算成功、什么结果算失败或该停、要跟谁比"写下来。** 尤其"失败"要单独定义清楚，而不是留成"没成功"的反面——否则跑完总能圆回来。

### 4. Idea 应该从实验信号里长出来

好的想法很少是凭空拍出来的，多半是从某个卡点、某个反常结果、某张不对劲的可视化里长出来的。所以每个新实验都该先讲清楚它**从哪来**：是上一轮的失败逼出来的，是某个遗留问题、某个异常结果，还是一篇论文给的启发。哪怕来自研究者自己的直觉，也要说明它怎么接回已经看到的证据。**AI 可以把想法的数量扩出去，但方向最好由真实信号来约束。**

### 5. 远程训练不能只看"已启动"

最烧钱的部分在远程 GPU。命令发上去之后，系统会以为它在跑，可实际上它可能第一秒就挂了，或者显卡根本没占上、日志半天不动、跑完也没产出结果，而人还在傻等。结论很简单：**跑起来之后第一件事不是走开，而是先确认它到底有没有真的在跑。** 远程实验的第一目标从来不是自动化，而是知道它有没有真实发生。

### 6. 工具要少而准

工具越多，模型越容易犹豫、误选，或被工具输出拖垮上下文。更稳的是让工具分工清楚：本地代码语义理解、精确字符串定位、外部文献检索、远程运行、结果归档，各用一件顺手的工具就够。**工具是为了减少上下文污染和重复劳动，不是为了堆能力。**

## 二、工作流大致是怎么走的

一轮实验从想法到结论，大致就是下面这条线。核心是一句话的分工：**讨论和判断交给 Claude，长任务的代码执行交给 Codex，最终科研判断留给人。**

```text
① 收集信息   →  ② 讨论方案  →  ③ 转成执行清单  →  ④ 代码实施
                                               │
⑦ 分析 + 下一步  ←  ⑥ 拉回日志/结果  ←  ⑤ 推远程训练 ┘
      │
      └→（更新当前真相，进入下一轮 ①）
```

1. **收集信息**：新一轮开始，先让 Claude 读当前状态和上一轮结果，把这轮要用的东西聚齐——相关代码、上一轮日志，必要时用 `smart-search-cli` 查一下文献、官方文档或某个方法的最新做法（它的检索结果还能落盘存证）。目的是给讨论一个干净、够用的上下文。
2. **讨论方案**：和 Claude 讨论这一轮要验证什么假设、怎么设计、什么算成功什么算失败，收敛成一份方案（spec）。这一步 Claude 走的是 `brainstorming` skill——它会主动追问、帮你把模糊需求聊清楚再落成方案。这是人和 Claude 一起做判断，也是整条链里最该慢下来的地方。
3. **转成执行清单**：方案批准后，把它转成一份给 Codex 的任务清单（CSV）。清单是执行的唯一状态源，每条任务的进度、验证、提交都记在上面，中断了也能恢复。
4. **代码实施**：切到 Codex，让它按清单写代码、跑本地的小验证（能不能导入、能不能编译、参数链路对不对）。这些便宜、快、确定的检查放本地做。推远程之前，还会用 `pre-run-implementation-review` 做一次实现层审查（为什么单设这道门见第四节），确认逻辑和数据流没问题再去烧 GPU。
5. **推远程训练**：代码推到远程 GPU 服务器，用 tmux 跑真正的训练和评估。用 tmux 起一个**持久会话**很关键——训练动辄几小时甚至更久，直接在普通终端里跑，本地一断网、ssh 一掉、终端一关，远程进程就跟着被杀了；放进 tmux 会话里，进程独立于你的连接存活，断开后随时能重新 `tmux attach` 回去看进度。发出去之后也别急着走，先确认它真的在跑（进程在、有 loss、显卡占上了）。
6. **拉回日志/结果**：训练完，把日志、指标、结果这些最小证据集拉回本地。日志和结果是"实验真的发生过"的唯一凭证。
7. **分析 + 下一步**：让 Claude 基于拉回来的真实结果分析这一轮——假设成立没有、有没有反常信号、能得出什么结论，然后更新"当前真相"，给出下一步建议。下一步就成了新一轮的起点。

整条链里，Claude 出现在两头（讨论、分析），Codex 在中间执行，人始终握着"要不要这么干、结果能不能这么说"的判断权。

## 三、如何使用这套工作流仓库

我会把工作流所需的配置层整理到 GitHub 分享，主要是这几样：

```text
.claude/                              # Claude Code 项目级配置（skills）
.codex/                               # Codex 项目级配置（skills）
AGENTS.md                             # 执行侧（Codex）规则
CLAUDE.md                             # 规划侧（Claude）路由 + 硬门禁
docs/superpowers/specs/TEMPLATE-spec.md   # 写方案 spec 的模板
issues/TEMPLATE.csv                   # 任务 CSV 的字段模板（状态机 schema）
```

上手三步：

1. **放进项目**：先给你的项目 `git init`（Codex 每完成一步会自动 commit，没有 git 闭环会断），再把上面这些文件放进项目根目录。
2. **改项目事实**：打开 `CLAUDE.md` 和 `AGENTS.md`，把末尾的项目事实换成你自己的——研究方向、baseline、主/辅指标、远程环境、artifact 目录、哪些结论必须有证据支撑。路由规则和硬门禁本身不用动。
3. **跑一轮**：开 Claude 讨论需求 → 生成 spec → 批准后转成 CSV → 切 Codex `/goal @issues/xxx.csv` 执行。第一轮别挑复杂模块，选个 baseline 复现或简单实验，目的是验证这条链能不能闭环。

除了上面这套配置，工作流还额外依赖两个搜索工具，需要单独安装：

- **`fast_context_search`**：本地代码的语义搜索（自然语言定位逻辑、调用链），比纯 `grep` 更适合"我不知道在哪但知道大概在干嘛"的调研。安装见 [面向小白的harness engineering实战（科研导向的infra搭建，本质是篇二创） (linux.do)](https://linux.do/t/topic/2260154/1)
- **`smart-search-cli`**：可保存证据的外部检索（论文、官方文档、工具版本），检索结果能落盘到 `search_evidence/`。安装见  [smartsearch](https://github.com/konbakuyomu/smartsearch)

## 四、仓库各部分的作用

要改得动，先知道每块管什么。整套东西分两层：**配置层**（给 agent 看的规则，机器消费）和**证据层**（人和 agent 共享的知识台账，`research_workspace/`目录）。

### 配置层

| 文件 | 作用 | 你改它会怎样 |
|------|------|--------------|
| `CLAUDE.md` | 规划侧 Claude 的路由和硬门禁，含 Claude/Codex 职责边界（Claude 只讨论+生成 CSV，不执行） | 改 Claude 的行为规则和项目约束；末尾追加项目事实 |
| `AGENTS.md` | 执行侧 Codex 的规则，核心是"按 CSV 持续执行到闭环" | 改 Codex 的执行行为和它认识的项目背景 |
| `.claude/` | Claude Code 挂载的 skills、agents、settings | 增删规划侧能力（如讨论、生成 CSV 相关的 skill） |
| `.codex/` | Codex 挂载的 skills 和配置 | 增删执行侧能力（如远程运行、拉取结果相关的 skill） |
| `docs/superpowers/specs/TEMPLATE-spec.md` | 一份 spec 该写哪些字段 | 增减你想在每轮实验里固定回答的问题 |
| `issues/TEMPLATE.csv` | 任务 CSV 的列和状态枚举 | 调整任务的状态机字段 |

### 证据层：`research_workspace/`

这是科研产物的统一工作区。仓库里给的是空壳结构，实验产物由你自己往里填。

它**单独 git 成一个独立仓库**，和放代码的主仓库分开管理（可以用 submodule，也可以就是主仓库里一个各自 `git init` 的子目录）。这么做有两个好处：一是代码提交和实验产物提交互不干扰——改一次模型代码是一次 commit，落一批实验结果是另一次 commit，两条历史各自干净；二是实验证据（日志、指标、分析）往往体量大、更新频繁，单独一个仓库不会把代码仓库的历史撑爆。前面工作流里"结果提交"那一步（`research-result-commit`），提交的就是这个 research_workspace 仓库，同时记下它关联的主仓库分支和 commit，方便日后对着代码回溯。

| 路径 | 作用 |
|------|------|
| `README.md` | 工作区入口和导航 |
| `STATE.md` | **当前真相**：现在仍然成立的结论、活跃路线、已废弃路线。每轮结束更新，下一轮先读它 |
| `00-实验记录.md` | **实验台账**：每次实验的索引和关键指标，只记索引不记长篇分析 |
| `11-模块规划.md` | 模块级规划台账 |
| `experiments/<ExpID>/` | 单次实验绑定的产物：远程拉回的日志/结果，以及这次实验的分析 |
| `experiments/_cross_experiment/<RouteID>/` | 跨实验、路线级的复盘 |
| `module_research/` | 模块论文 / 源码调研（外部检索证据也存这里） |
| `papers/` | 论文材料 |
| `commands/` | 远程命令、shell 片段 |
| `archive/` | 过时草案 |

这层的设计动机就是核心思想第 1 条：把不同类型的记忆分开存——`STATE.md` 管"现在信什么"，`00-实验记录.md` 管"历史都跑过什么"，`experiments/` 管"单次实验的原始证据"，谁也别污染谁。

### 配套的实验 skills

除了通用配置，`.claude/` / `.codex/` 里还带了几个**项目特定的 skill**，专门把"跑完 → 拉日志 → 登记 → 分析 → 提交"这段流水自动化：

- **生成远程运行命令**（`autodl-remote-run-snippet`）：拼好 `git 同步 + 训练/评估` 的命令块，直接贴到远程 tmux 里跑。
- **拉回日志/结果**（`autodl-remote-pull-manifest`）：从远程把最小证据集（console log、指标、结果文件、可视化）拉到 `research_workspace/experiments/<ExpID>/` 下。
- **登记台账**（`exp-results-ingest-local`）：把这次实验的索引和关键指标（你的主/辅指标）写进 `00-实验记录.md`。
- **证据分析**（`exp-analysis-hen`）：基于拉回的日志/指标，生成"假设成立没有、下一步做什么"的分析报告（H→E→N）。
- **结果提交**（`research-result-commit`）：把这一轮的研究产物合并成一次提交，关联上代码的分支和 commit。

还有一个 `pre-run-implementation-review`，作用是在**代码写完、正式推去远程跑之前，做一次实现层的审查**：对照这轮的意图和方案，检查代码逻辑、数据流、参数链路对不对，发现问题（blocker）就先修，别带着 bug 去烧 GPU。它的存在有两个原因：

- **替代 TDD/RED/test-first，省 token**：原版 superpowers skills 走的是 TDD / RED / test-first 那一套——先写失败测试再写实现，对科研代码来说既不太适用，又非常吃 token。本工作流干脆不用它，改成在运行前做一次轻量的实现审查来把关。
- **防"能跑但跑错"**：实际用下来遇到过 Codex 写的代码能编译、能跑通，但**数据流是错的**（比如张量拼错、mask 用反、某个分支没接上）。这种 bug 本地小验证不一定发现，一旦推上远程，白白烧掉几小时 GPU 和时间才发现结果没意义。运行前审查就是专门拦这一类"表面正常、实则跑错"的问题。

需要提醒的是：`.codex/skills` 里的一部分 skill **不是原版，而是按这套科研工作流改过的**——比如拉日志的路径约定、台账和分析报告的落盘位置、提交时的关联字段，都对齐到了本工作流的目录结构。所以直接拿去用之前，最好翻一下这些 skill 的内容，确认里面写死的路径、文件名、字段和你的项目对得上（这也是下一节"适配"要处理的重点之一）。

**这里有一个关键前提，也是适配时最容易漏的一点：这些 skill 依赖你的实验代码把日志写到约定好的位置。** 换句话说，你需要在自己的训练/评估代码里加一套日志系统——把控制台输出、指标、最终结果（比如 `summary.json` / `results.json`）、可视化，统一写到远程实验根目录（`EXP_ROOT`）下约定的子目录里。skill 做的事，就是去这些约定的日志文件夹里，把对应文件拉回来、汇总指标。

所以把这套工作流搬到自己的项目时，日志这一环要对齐：要么让你的日志输出对齐 skill 期望的目录结构和文件名，要么改 skill 里的路径约定，让它去你实际的日志目录拉。只要"代码往哪写日志"和"skill 去哪拉日志"这两头对上，后面的登记、分析、提交才能自动接上。

## 五、如何适配到自己的任务

这套东西是可迁移的骨架，不是照抄就能用的成品。换到你的课题上，至少改这几处：

- **项目事实**：`CLAUDE.md` / `AGENTS.md` 末尾——研究方向、baseline 和复现口径、主指标和辅助指标、数据集和评测协议、远程环境、artifact 目录。这是让 AI"知道你在做什么"的关键，改到位能省掉大量重复追问。
- **评测口径与脚本**：把示例里的主指标、评测方式、远程脚本路径换成你自己的。
- **证据台账**：`research_workspace/` 按你的实验往里填；`STATE.md` 用你的方向重写第一版当前真相。
- **过度声明的红线**：写清楚哪些结论必须有真实训练/评估证据才能下——比如"没有结果文件不许声称指标提升""单次运行的高点只能算 tentative"。这类硬门禁是防 AI 自欺的核心。
- **改远程/日志相关的四个 skill**：下面这四个 skill 里写死了不少本项目的约定（日志路径、指标名、脚本解析、台账格式），是适配时最需要动的地方。最省事的做法，是直接开一个会话，让 AI 把这四个 skill 读一遍，再对照你的任务改：
  - `autodl-remote-run-snippet`：从 `scripts/` 里解析训练/评估脚本、拼远程命令。要对齐你自己的脚本名、参数和远程环境。
  - `autodl-remote-pull-manifest`：里面有一份固定的"最小拉取清单"（`EXP_ROOT` 下的 `results.json`、`train_console.log`、`eval/**/metrics/**` 等）。要改成你的代码实际写日志/结果的路径和文件名。
  - `exp-results-ingest-local`：解析 `summary.json` 里的指标（本项目是 <主指标>/<辅助指标>）写进台账。要对齐你的指标名和结果文件 schema。
  - `exp-analysis-hen`：基于拉回的指标做 H→E→N 分析，默认围绕分割指标。要把关注的指标和分析逻辑换成你课题的。

  这四个是一条流水（生成命令 → 拉日志 → 登记 → 分析），改的时候盯住一条主线：**你的实验代码把日志/指标/结果写到哪、用什么文件名，这四个 skill 就得照着那套路径去拉、去解析。** 两头对齐了，整条自动化才接得上。

一个建议：先用最小链路跑顺几轮（baseline 复现、简单实验），熟悉了讨论→执行→远程→分析的节奏，再把复杂模块和更严格的门禁加上。

## 六、最后的思想

这套工作流能长期运转，不是因为某个模型特别聪明，也不是因为装了很多工具，而是因为它把科研任务拆成了几种**不同的记忆**，并让 Claude 和 Codex 各管一段：当前真相、实验台账、实验前判据、想法来源、远程证据、单次分析、执行交接，各有各的位置。

AI 的优势是吞吐量和执行力，人的优势是问题表述、抽象、taste 和判断边界。面向科研的 Harness Engineering，就是把这两者接起来：**让 AI 在可验证的轨道上高速推进，同时让每个结论都能回到一个清楚的问题、一个定死的判据、一组真实证据。**

如果你要迁移到自己的项目，先回答几个问题：我的当前真相写在哪里？我的实验台账写在哪里？我的想法从哪些证据里来？我的判断标准怎么在跑之前定死？我的远程运行怎么证明真的跑了？把这些答清楚，再接入 Claude、Codex 和少量 skill，工作流才会真正帮你做科研，而不是帮你更快地产生不可复现的幻觉。
