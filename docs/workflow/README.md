# 面向科研的 Harness Engineering：用 Agent 做实验的思想与工作流

这套工作流最初是在一篇社区教程[面向小白的 harness engineering 实战](https://linux.do/t/topic/2260154)的基础上改出来的。那篇讲的是怎么把 agent + 任务清单这套架构在科研项目里搭起来；本文讲的是为什么这么设计、一轮实验怎么走、以及每个部分在管什么，方便你改成自己的。

用 AI 做科研，跑得住的关键不是模型多聪明或者工具多，而是一个判断：

> 科研 harness 要管的是上下文、实验前的判据、远程运行的证据、结果归档和当前结论。让 AI 在边界清楚的地方快速执行，让人保留问题定义、验收标准和科研判断。

## 一、几条原则

现阶段可靠的 AI 科研不是全自动，而是人在环里的半自动。AI 适合做重复劳动、代码实现、实验调度、日志整理和初步分析；危险的是让它在混乱的上下文里自己定义问题、自己判断成功、自己解释结果。下面几条是这套工作流所有机制的来源。

### 1. 上下文比工具数量重要

重点不是把材料一股脑塞进去，而是让模型只读当前这件事需要的那部分。

常见的污染：主会话里混进环境安装报错、下载日志、无关论文摘要；一个模型既搜论文又提想法又写实现，最后困在自己前面说过的话里；旧实验的结论和当前事实混在一起，下一轮就把已经废弃的东西当成真的。

对策是一个习惯：把"当前在做什么""这次实验的事实""跨实验的结论""原始日志"分开存、分开读。文件只是载体，真正要管的是这些东西进入模型的顺序和粒度。

### 2. Baseline 是锚点，不是前置杂活

最常见的翻车方式，是让 AI 直接提一个想法，然后从零写一套代码去验证。没有 baseline 的 AI 科研几乎一定会飘。深度学习里多数有价值的工作也不是从零造系统，而是在一个跑得通、信得过的 baseline 上做控制变量。一个新想法值不值钱，只有在同一个 baseline、同样的评测口径下才比得出来。

### 3. 实验前把判断标准定死

AI 很擅长事后解释：结果没提升，它能说"发现了有趣现象"；对照失败，它能建议"再试个变体"。只要事先没约定什么算成功，整个过程就会滑向先射箭再画靶。

所以在写代码之前，就要把想验证什么、什么结果算成功、什么结果算失败该停、跟谁比写下来。尤其"失败"要单独定义清楚，而不是留成"没成功"的反面 —— 否则跑完总能圆回来。

### 4. 想法应该从实验信号里长出来

好想法很少凭空拍出来，多半来自某个卡点、某个反常结果、某张不对劲的可视化。所以每个新实验都该先说清楚它从哪来：上一轮的失败逼出来的，还是某个异常结果、某篇论文的启发。AI 可以把想法的数量扩出去，但方向最好由真实信号约束。

### 5. 远程训练不能只看"已启动"

最烧钱的部分在远程 GPU。命令发上去之后，系统会以为它在跑，但它可能第一秒就挂了，或者显卡根本没占上、日志半天不动、跑完没产出结果，而人还在等。

启动之后第一件事不是走开，而是先确认它到底有没有真的在跑。远程实验的第一目标不是自动化，是知道它有没有真实发生。

### 6. 工具要少而准

工具越多，模型越容易犹豫、误选，或者被工具输出拖垮上下文。让工具分工清楚：本地代码理解、精确字符串定位、外部检索、远程运行、结果归档，各一件顺手的就够。工具是为了减少污染和重复劳动，不是为了堆能力。

## 二、一轮实验怎么走

```text
① 定方案  →  ② 转执行清单  →  ③ 写代码 + 本地验证  →  ④ 运行前审查
                                                          │
⑦ 更新结论  ←  ⑥ 拉回证据  ←  ⑤ 远程训练/评估  ←────────┘
     │
     └→ 进入下一轮 ①
```

**① 定方案。** 先读当前状态和上一轮结果，把这轮要用的东西聚齐 —— 相关代码、上一轮日志，必要时查文献。然后讨论这轮验证什么假设、怎么设计、什么算成功什么算失败，收敛成一份 spec。这是整条链里最该慢下来的地方，也是人和 AI 一起做判断的地方。spec 要你逐字确认才算批准。

**② 转执行清单。** 批准的 spec 转成一份 CSV。这份 CSV 是执行状态的唯一来源 —— 每条任务的进度、验证、提交都记在上面，中断了也能从它恢复。

**③ 写代码 + 本地验证。** 按清单实现，跑本地的小验证：能不能导入、能不能编译、参数有没有真的传到该去的地方。这些便宜、快、结果确定的检查放本地做。

**④ 运行前审查。** 推远程之前先过一道。这道门的存在理由见[第四节](#四运行前审查在看什么) —— 简单说，科研的翻车方式是"代码全对、测试全绿、GPU 跑了二十小时，方法却是错的"，而这个代价发生在"做出来"和"审查"之间。

按改动风险分档：文档、状态、纯测试的改动不用审；只改运行绑定、科学内容没变的，探针过了就放行；改了模型、损失、数据、指标、计算入口的，要先跑一次隔离的短 smoke（1–100 步），再做一次独立审查。

**⑤ 远程训练/评估。** 通过 rrctl 提交到远程 GPU。启动后 30 秒到 2 分钟内做一次首步检查：进程在不在、有没有出现第 1 步、loss 是不是有限值、显卡占上没有、checkpoint 目录建了没有。过了才算真的在跑；不过就别走开。之后转低频巡检，不用一直盯着。

**⑥ 拉回证据。** 只拉结论需要的部分 —— 结果文件、指标摘要、必要日志。逐样本的追踪数据留在远端，要查再定点取。

**⑦ 更新结论。** 基于真实结果判断：假设成立没有、有没有反常信号、能得出什么结论。然后更新三处：这次实验的事实（`record.json`）、这次实验的结论（`analysis.md`）、如果认知真的变了，更新跨实验的结论（`CONCLUSIONS.md`）。

人始终握着"要不要这么干、结果能不能这么说"的判断权。

## 三、执行那一下，交给 Goal

到了执行阶段，Codex 的长任务可以这样启动：

```text
/goal @issues/<任务目录>/<任务清单>.csv
```

这里有三个分工：

- CSV 说明这批工作具体做什么、怎么验收。
- Mission 工作流说明怎样实现、检查、运行和收尾。
- Goal 让同一个 Codex 会话跨回合继续推进目标。

CSV 仍然是任务进度的依据。Goal 不会把未完成的验证变成完成，也不会替你扩大实验预算。普通模式中的 `mission <CSV 路径>` 同样可以执行清单；长任务使用 Goal，是为了让持续推进这件事有明确的目标。

Goal 的开启、暂停和恢复见[执行说明](usage.md#用-goal-模式执行-csv)。

## 四、运行前审查在看什么

运行前审查会把方案与实际实现放在一起核对：采样策略有没有真正进入数据流程，损失是否按约定计算，评估是否沿用正确的数据和指标口径。

短运行能提供代码实际执行的证据，审查则结合这些证据判断实现是否符合科学意图。这样可以在正式长训练前发现问题，并明确还需要修复或验证的部分。方法最终有没有效果，仍由正式实验结果回答。

## 五、训练开始后，谁来等

科研任务和普通代码任务有个明显区别：代码改完，可能还要等几小时才能看到结果。

这段时间由 rrctl 管理远程运行。启动之后先确认有真实进展，再按约定检查状态。正常等待由普通程序完成，agent 无需隔一两分钟重新读日志、写一段进度分析。

在同一会话持续等待时，结果返回后，agent 接着处理原 CSV。成功就核对并收集结果，失败就查看诊断证据。用户不需要额外告诉它“训练好了”。

日志短暂停顿、保存 checkpoint 时变慢，需要结合运行情况判断。进程退出以后，也要分清正常完成、失败和主动停止。这些运行事实决定接下来怎样处理任务。

普通程序的检查本身不调用语言模型。宿主工具需要续等、或者出现新结果要处理时，agent 仍可能产生调用，因此这里的目标是减少无效消耗，不承诺训练期间的账单绝对为零。

## 六、实验多了，怎样把证据和结论管清楚

只有几次实验时，靠目录名和记忆还能找到结果。实验积累到几十次、上百次以后，就容易出现两种混乱：大量日志挤进工作区，真正有用的分析反而找不到；旧方案、新结果和失败尝试混在一起，已经推翻的判断又被当成下一轮的起点。

实验管理要把这两件事一起处理：让原始证据有地方可查，也让研究判断能够持续积累和修正。

### 1. 原始证据与研究判断分开放

训练日志可以证明实验发生过，但几万行日志并不能直接回答“我们现在知道了什么”。这部分材料需要保留，也需要经过分析，才能进入下一轮讨论。

不同材料各回答一个问题：

| 材料 | 回答什么 |
|---|---|
| `remote_artifacts/<ExpID>/<RunID>/` | 这次运行留下了哪些原始结果和证据 |
| 每个实验的 `record.json` | 这个实验对应什么代码、哪些运行和哪些已确认的机器事实 |
| 实验的 `analysis/analysis.md` | 结果怎样解释，有什么发现、限制和下一步建议 |
| `EXPERIMENTS.csv` | 做过哪些实验，可以去哪里查看 |
| `CONCLUSIONS.md` | 当前有哪些得到支持、尚不确定或已经被否定的判断 |
| `STATE.md` | 当前主线、瓶颈、正在进行的实验和下一步是什么 |

原始证据放在项目根的 `remote_artifacts`，默认不进入 Git，也不作为 agent 每轮都读取的上下文。大型 checkpoint、张量和逐样本追踪数据按需留在远端。`research_workspace` 保留实验事实、分析和结论，人和 agent 平时从这里进入研究。

### 2. 先读概要，再按问题查证据

每次开始讨论，都把所有历史日志重新读一遍，成本很高，也容易把注意力带离当前问题。平时先看当前状态和有效结论，找到相关实验后，再展开细节。

```text
STATE.md → CONCLUSIONS.md → EXPERIMENTS.csv → record.json → analysis/analysis.md
                                                               ↓ 需要核验时
                                               对应运行的 remote_artifacts
                                                               ↓ 仍不足时
                                                   远端完整原始数据
```

这就是渐进式披露在科研记录中的用法。比如要核对某个提升是否稳定，先找到对应实验和分析，再看所需的重复运行结果。明确要查的问题后，选取相应证据，不递归批量读取整个原始产物目录。

### 3. 记清实验从哪里来、在和谁比较

实验之间需要有关系。某次实验是在上一轮基础上修改了采样策略，另一次是在同样条件下复查稳定性，还有一次可能发现早期评测设置不成立。这几种关系会影响我们怎样理解结果。

每轮分析都应说明：沿用了哪个实验，改变了什么，和哪组结果对照，是复现已有发现，还是发现了需要修正的旧结论。不能只凭目录时间或名称相近，就认定两个实验存在继承关系。

对照条件也要一起核对。数据划分、评测方法、指标单位和多次运行的汇总方式不同，两个分数就未必能直接比较。算提升幅度之前，先确认比较的是哪一次基线运行，以及它和当前实验是否采用可比较的条件。

这些关系先在实验分析中写清楚并关联来源。当前还不能自动整理的关系或对照字段保留待补状态，不靠手改生成记录去补造依据。

### 4. 保留结论状态，也保留失败经验

“训练跑完了”“实验条件有效”“假设得到支持”是不同的判断。程序顺利结束之后，仍可能没有观察到收益；如果后来发现数据或评测条件有问题，还需要重新判断这份结果能否作为证据。

结论要说明目前处于什么状态：待验证、已有支持、证据有分歧、被否定，或者已被新结论取代。支持它的实验和限制它的实验，都应该能找到。

旧实验不会因为结论被推翻就失去价值。保留它以及判断改变的原因，下一轮才能知道这条路曾经为什么失败。没有提升的实验，也可以帮助我们排除一种解释，或者发现还需要检查的条件。

### 5. 一处记录事实，汇总从事实中生成

每个实验用一份 `record.json` 保存能由任务和产物确认的事实，`EXPERIMENTS.csv` 从这些记录生成。要修正事实，应回到来源核对后重新生成，避免在几个表格里分别维护同一个指标。

如果以后需要实验关系图或其他展示，也应基于已确认的记录生成，让汇总能够重建。图表方便查看，原始记录和分析仍然提供依据。

`STATE.md` 保持几屏以内，按已确认的进展更新当前主线和下一步，不堆入每次巡检的细节。任务执行状态继续由 Mission CSV 管理，实验索引用来查研究历史，两者各有用途。

### 6. 新实验开始前，先利用已经付过的成本

准备继续一个方向时，先查当前结论、实验索引和相关分析。若命中了已经尝试过的路线，就说明这次的新变量或复核目的。重跑可以为了验证稳定性，也可以为了检查旧结论，但应当知道这次投入准备回答什么问题。

历史记录不完整时，优先整理当前主线、关键实验和重要失败。旧实验在被重新引用、用于对照或支撑论文结论时，再补齐必要依据，逐步整理即可。

Hindsight 是可选的辅助检索服务，可以帮助寻找相关历史材料。找到内容后，仍要核对它的来源、状态和适用条件；本地科研记录也可以独立使用。官方安装仓库和配置见[接入教程](installation.md#可选-hindsight)。

## 七、配套工具各用在什么地方

模板已经包含 Mission 的相关技能、rrctl 和科研记录程序。中文文档处理需要另外准备 `humanizer-zh`，下面的检索与架构工具则可以按需选择。

[`fast-context-mcp`](https://github.com/SammySnake-d/fast-context-mcp) 是可选的代码语义检索工具，通过 `fast_context_search` 理解本地代码。比如先找到采样逻辑经过哪些模块、有没有现成实现可以复用，再去读具体文件和修改代码。

[`smart-search`](https://github.com/konbakuyomu/smartsearch) 是可选的外部资料查询工具，配合 `smart-search-cli` skill 使用。论文、工具文档和版本行为需要查来源时，可以从这里取得材料，再回到当前实验的问题上。

[`humanizer-zh`](https://github.com/op7418/Humanizer-zh) 用来整理面向人的中文方案和交付说明。本项目要求安装它，让报告读起来更清楚；指标、路径和代码标识符仍保留原样。

涉及架构取舍时，还可以加上 [`lite-arch` / `lite-arch-recall`](https://github.com/flowing-water1/lite-arch)。例如记录为什么采用当前模块划分，下次改同一部分时先回看当时的原因。这是可选项，可以按项目需要接入。

这些工具的准备位置，以及项目里具体要改哪些文件，都在[项目接入与配置](installation.md)中。接入之后，按[日常使用指南](usage.md)跑一轮熟悉的小任务，比一上来堆很多实验更容易看出哪里还没有对接好。
