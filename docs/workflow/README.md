# 面向科研的 Harness Engineering：设计哲学与核心机制

科研场景下的 Harness Engineering 与普通软件工程有本质区别：**软件工程关注“改代码 -> 跑单测 -> Git 提交”，而科研实验的核心矛盾是“高昂算力成本、长周期异步等待、数值指标真实性与假设持续演进”。**

通用 Coding Agent 在科研中极易遭遇三大翻车陷阱：
1. **上下文污染与事后画靶**：海量日志冲垮上下文，指标下跌时 Agent 本能地事后合理化（“观察到有趣现象，建议换个变体”），失去科学严谨性。
2. **算力空耗与静默假死**：远程训练启动后，CUDA OOM、进程死锁或 Loss NaN 导致 GPU 空烧，Agent 却在盲目轮询或直接休眠。
3. **证据漂移与认知丢失**：数十次实验后，推翻过的旧假设被再次拾起，论文结论无法追溯到具体的代码 commit 与原始产物。

为了锁死这三大风险，本工作流确立了以下核心原则与机制。

> **核心判断**：
> 科研 Harness 要管的是**上下文粒度、实验前的判据、远程运行的物理证据、结果归档和当前结论**。
> 让 AI 在边界清楚的地方快速执行，让人始终保留问题定义、验收标准和科研判断。

---

## 一、四条核心原则

### 1. 上下文比工具数量重要
* **痛点**：上下文塞的材料越多，模型越容易被早期噪音与海量日志冲垮。主会话中混入编译报错、数万行下载或训练日志；同一个模型既做检索又提方案又写实现，最终困在自己的历史回复中；旧实验被推翻的结论与当前事实混淆，下一轮容易把废弃路线当成真理。
* **机制**：把“当前在做什么（`STATE.md`）”、“跨实验认知（`CONCLUSIONS.md`）”、“本次实验事实（`record.json`）”与“海量原始证据（`remote_artifacts/`）”做**物理级隔离**。Agent 平时只读紧凑概要，严禁递归批量读取原始日志，仅在核验特定疑点时定点调阅。

### 2. 实验前把判断标准定死
* **痛点**：LLM 具备极强的事后合理化（Post-hoc Rationalization）倾向。实验没提升，它能解释为“发现了有趣的现象”；对照失败，它能建议“再试一个变体微调”。只要事先没有定死判据，研究就会滑向**先射箭再画靶**。
* **机制**：动代码前必须完成 Spec 并由人批准。白纸黑字写死：想验证什么假设、跟哪个 Baseline 在什么协议下比、主指标达到多少算成功、什么结果算失败该停。**“失败”必须被单独定义清楚**，而不是留成“没成功”的反面，杜绝跑完后强行圆场。

### 3. 远程训练不能只看“已启动”
* **痛点**：科研最昂贵的是远程 GPU。命令发上去后，系统返回“已启动”，但极可能第一秒就因 CUDA OOM、路径错误或死锁挂掉；或者显卡根本没占上、日志不动，人与 Agent 却误以为在正常推进。
* **机制**：启动后第一件事不是走开，必须通过**首步验证（First-step Gate）**：启动 30 秒至 2 分钟内，严格核对“进程真实存活、显存占上、step >= 1、Loss 为有限非 NaN 数值、checkpoint 目录建立”。首步不过绝不走开；过了才交由 `rrctl` 低频挂机。

### 4. 工具要少而准
* **痛点**：工具越多，模型越容易犹豫、误选、频繁试错，甚至被工具的冗余回显拖垮上下文。堆砌能力往往导致工作流不可靠。
* **机制**：分工明确，各配一件顺手工具：
  - 本地代码理解与精准定位；
  - 远程托管运行与生命周期管理（`rrctl`）；
  - 本地轻量数据处理与指标脱水；
  - 结构化实验事实与记忆检索。
  工具是为了减少上下文污染和重复劳动，不是为了堆砌功能。

## 二、一轮实验生命周期

```text
① 定方案 (Spec)      人机讨论假设、Baseline 与死标准（逐字批准）
      ↓
② 转清单 (CSV)       生成任务执行唯一事实源，逐行推进与状态恢复
      ↓
③ 本地验证 + 短运行   本地快速检查导入与参数链路；改动核心逻辑跑 1~100 步 smoke
      ↓
④ 运行前审查 (PRERUN)  只读 fresh 子会话审查实现与 Spec 是否一致，严防伪跑
      ↓
⑤ 远程托管 (rrctl)    启动后必过首步检查（显存/Step/Loss）；过门后进入静默等待
      ↓
⑥ 证据拉回与脱水      仅拉回 summary.json、指标与必要日志，大型数据留远端
      ↓
⑦ 事实与结论沉淀      更新单次机器事实 record.json、分析 analysis.md；
                     若认知更新，沉淀至独立 Git 的 CONCLUSIONS.md
```

1. **定方案 (Spec)**：先读当前状态和上一轮结果，明确假设、对照条件、主指标阈值与停止标准。Spec 经用户逐字确认后方可冻结。
2. **转清单 (CSV)**：批准的 Spec 转为任务 CSV。CSV 是执行状态的唯一事实源，任务进度、代码提交均在其中记账，随时可断点恢复。
3. **写代码与本地验证**：按清单实现，完成快速验证（导入、编译、参数传递链路）。涉及模型、数据、损失等核心逻辑改动的，必须执行 1~100 步短 smoke。
4. **运行前审查 (PRERUN)**：长训练前由独立只读子会话对照 Spec 审查实现与 short-smoke 产物，严防“代码全对但科学方法写错”。
5. **远程训练/评估**：通过 `rrctl` 托管提交至远程 GPU。严格执行首步检查，通过后转入静默等待，无需 Agent 频繁打扰。
6. **拉回证据**：仅拉回结论必需的关键产物（`summary.json`、指标摘要、关键日志），原始巨型张量与样本追踪数据留在远端。
7. **更新结论**：基于真实结果更新单次实验机器事实（`record.json`）与实验分析（`analysis.md`）。若产生跨实验新认知，同步更新独立 Git 管理的 `CONCLUSIONS.md`。
