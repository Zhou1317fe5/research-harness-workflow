# 用 Mission + Goal 做科研：把一轮实验从头到尾接起来

假设你准备给现有基线换一种采样策略。agent 改好了代码，训练也启动了。接下来还得确认：新策略有没有真正生效，评估读的是不是这次的 checkpoint，最后的成绩能不能和基线直接比较。

这些事如果只留在聊天里，下一轮讨论就得重新翻一遍。等实验多起来，“这份结果是哪版代码跑的”“这个想法上次为什么没继续”也会变成问题。

这套工作流把这些事情放进同一轮实验里处理。先把方案讨论清楚，形成任务清单，再让 Codex 持续执行；远程运行、结果分析和研究记录也一起跟上。

先看一遍完整的顺序：

```text
讨论这轮想验证什么
        ↓
写成方案（Spec），确认对照、预算和验收标准
        ↓
Mission 生成任务清单（CSV）
        ↓
Codex /goal 引用这份 CSV
        ↓
代码实现与本地验证 → 短运行与必要的实施审查
        ↓
rrctl 运行远程实验，等待完成或需要处理的异常
        ↓
核对结果、完成分析与交付、保存科研记录
        ↓
带着这一轮的发现，讨论下一轮
```

如果你想直接动手，接着看[项目接入与配置](installation.md)。项目已经接好了，就看[日常使用指南](usage.md)，里面会用一个例子走完这条链。

## 1. 先把这轮实验说清楚

“帮我优化一下模型”和“在同一评测条件下，验证新采样策略是否改善基线”，交给 agent 后会产生很不一样的任务。

后一个说法还有不少内容需要补齐：具体改哪里，和哪次基线比较，允许用多少资源，什么情况下停止。花时间把这些问题对齐，后面才容易判断工作有没有做对。

你可以先和 Claude 讨论，也可以在 Codex 中完成这一步。讨论形成的共识写进 Spec，由用户确认。下一步生成 CSV 时，实现、验证、运行和结果分析都有明确的出处。

这里用到的 `mission` 是工作流入口。它根据你给的是研究需求、方案还是已有 CSV，接到相应的处理步骤。具体输入方式放在[使用指南](usage.md#先讨论这一轮到底要验证什么)里，不需要一开始就记住所有技能名。

## 2. 为什么还要有一份 CSV

方案里可能只有一句“比较新旧采样策略”。执行时，这句话至少涉及代码修改、确认采样行为、运行对照、核对指标和整理分析。漏掉其中一项，最后那张结果表就可能少了依据。

CSV 把这些工作逐项列出来，同时记录进度和完成证据。agent 做完一项，就按对应的验收要求检查；整批工作结束后，还要回头看是否回答了原先的问题。

所以读交付时，我们可以沿着“任务要求 → 实际改动 → 验证结果”检查。某项工作没能完成，也应该留下原因和影响，方便判断还能推进哪些部分。

代码和科研记录会在合适的阶段分别提交。以后需要复查实验，能找到当时的实现和分析，不必靠聊天里的记忆猜。

## 3. 执行那一下，交给 Goal

到了执行阶段，Codex 的长任务可以这样启动：

```text
/goal 按仓库的 CSV 执行流程完成 @issues/<任务目录>/<任务清单>.csv，逐项验证并完成结果交付与提交。
```

这里有三个分工：

- CSV 说明这批工作具体做什么、怎么验收。
- Mission 工作流说明怎样实现、检查、运行和收尾。
- Goal 让同一个 Codex 会话跨回合继续推进目标。

CSV 仍然是任务进度的依据。Goal 不会把未完成的验证变成完成，也不会替你扩大实验预算。普通模式中的 `mission <CSV 路径>` 同样可以执行清单；长任务使用 Goal，是为了让持续推进这件事有明确的目标。

Goal 的开启、暂停和恢复见[执行说明](usage.md#用-goal-模式执行-csv)。

## 4. 训练开始后，谁来等

科研任务和普通代码任务有个明显区别：代码改完，可能还要等几小时才能看到结果。

这段时间由 rrctl 管理远程运行。启动之后先确认有真实进展，再按约定检查状态。正常等待由普通程序完成，agent 无需隔一两分钟重新读日志、写一段进度分析。

在同一会话持续等待时，结果返回后，agent 接着处理原 CSV。成功就核对并收集结果，失败就查看诊断证据。用户不需要额外告诉它“训练好了”。

日志短暂停顿、保存 checkpoint 时变慢，需要结合运行情况判断。进程退出以后，也要分清正常完成、失败和主动停止。这些运行事实决定接下来怎样处理任务。

普通程序的检查本身不调用语言模型。宿主工具需要续等、或者出现新结果要处理时，agent 仍可能产生调用，因此这里的目标是减少无效消耗，不承诺训练期间的账单绝对为零。

## 5. 跑完之后，下一轮能留下什么

一轮实验的交付，应该让你看清这次改了什么、观察到了什么，以及这些结果能说明多少问题。

“程序正常退出”和“新策略有效”需要分别判断。新方案没提升，也可能是有价值的结果；它帮助我们排除一种解释，或者发现下一步应该检查的条件。

科研记录会把这些内容接到后续工作中：

`STATE.md` 说明当前在做什么，`CONCLUSIONS.md` 保留仍然有效的判断，每次实验的分析保存具体结果与依据。旧方案被替换后，原来的记录仍然可查，也会说明为什么不再沿用。

下一轮先读当前状态，再查相关实验。需要核验细节时，才回到原始日志和结果。这样，过去的尝试能够被利用，过时的判断也不容易混进当前方案。

Hindsight 是可选的辅助检索服务，用来从较多历史材料中寻找相关来源。本地科研记录也可以独立使用。它的官方安装仓库和项目配置都放在[接入教程](installation.md#可选-hindsight)。

## 6. 配套工具各用在什么地方

模板已经包含 Mission 的相关技能、rrctl 和科研记录程序。中文文档处理需要另外准备 `humanizer-zh`，下面的检索与架构工具则可以按需选择。

[`fast-context-mcp`](https://github.com/SammySnake-d/fast-context-mcp) 是可选的代码语义检索工具，通过 `fast_context_search` 理解本地代码。比如先找到采样逻辑经过哪些模块、有没有现成实现可以复用，再去读具体文件和修改代码。

[`smart-search`](https://github.com/konbakuyomu/smartsearch) 是可选的外部资料查询工具，配合 `smart-search-cli` skill 使用。论文、工具文档和版本行为需要查来源时，可以从这里取得材料，再回到当前实验的问题上。

[`humanizer-zh`](https://github.com/op7418/Humanizer-zh) 用来整理面向人的中文方案和交付说明。本项目要求安装它，让报告读起来更清楚；指标、路径和代码标识符仍保留原样。

涉及架构取舍时，还可以加上 [`lite-arch` / `lite-arch-recall`](https://github.com/flowing-water1/lite-arch)。例如记录为什么采用当前模块划分，下次改同一部分时先回看当时的原因。这是可选项，可以按项目需要接入。

这些工具的准备位置，以及项目里具体要改哪些文件，都在[项目接入与配置](installation.md)中。接入之后，按[日常使用指南](usage.md)跑一轮熟悉的小任务，比一上来堆很多实验更容易看出哪里还没有对接好。
